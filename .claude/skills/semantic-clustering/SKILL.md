# Універсальний збір семантики (semantic core)

Збирає й кластеризує ядро для БУДЬ-ЯКОЇ ніші з **вимірюваним** покриттям. Вхід: тема / категорія / сід-фрази або вивантаження в `clients/<проєкт>/inbox/` + (опціонально) сайт клієнта й конкуренти. Якщо проєкт не названо - спитай.

## Принцип №1 - дані, а не здогадки; покриття вимірюється
Частотності, обсяги, позиції - лише з API чи вивантажень, не вигадувати. І: **один сід майже ніколи не дає повного ядра.** Покриття залежить від типу ніші, тому збираємо багатоканально (Кроки 1-2) і ПЕРЕВІРЯЄМО його цифрою (Крок 3), а не «на око».

## Крок 0. Тип ніші - визначає стратегію збору
- **Категорійно-словна**: більшість запитів містять слово категорії (кепки, кава, кросівки). Розширення сідом за словом категорії дає 85-98%.
- **Франшизно-брендова**: топ-запити НЕ містять слова категорії, а містять франшизу чи бренд (фігурки → «funko pop / pop mart / щенячий патруль»; автозапчастини → марка авто; техніка → бренд). Один сід категорії дає 40-50% - замало.

Як визначити: `python scripts/serpstat_api.py top "<головний сід>"` → візьми URL лідера → `url-keywords` → якщо багато ВЧ-ключів БЕЗ слова категорії → ніша франшизна, потрібні бренд- і франшиз-сіди та (головне) url-keywords конкурентів. (Перевірено: фігурки одним сідом «фігурки» = 41%, кепки сідами = 96%.)

## Крок 1. Збір сідами - усі форми й синоніми, обидві мови
- База + **синоніми** (кепка/бейсболка/панама; кава/кофе; кросівки/кеди/снікерси; фігурки/статуетки).
- **Однина + множина, RU + UA** - форми різняться, сід ловить лише свою: «кепка жіноча» ≠ «жіночі кепки», «панама» не ловить «панамка». Слова, спільні для RU/UA (кепка/панама), покривають обидві мови одним сідом.
- Реверс порядку слів НЕ потрібен (розширення й так покриває: «кросівки жіночі» дав +3 до «жіночі кросівки»).
- Частотність обов'язкова: `python scripts/serpstat_api.py keywords "<seed>" --min-vol 10 --max-pages N` (UA, база g_ua) або `dataforseo_api.py volume` (інші ринки). Є у вивантаженні - використовуй її; немає - добери; ключ без частотності в кластери мовчки не йде.

## Крок 2. Конкуренти - обов'язковий канал (ловить те, що пропускає сід)
`top "<сід>"` → 2-4 URL категорій конкурентів → `url-keywords` кожного. **Для франшизних ніш це ОСНОВНЕ джерело** (каталоги конкурентів ранжуються за товарними франшиз-запитами без шуму «ігри / мультика», який тягне голий франшиз-сід). + сайт клієнта, якщо є: `url-keywords` / `domain-keywords`.

⚠ Голий франшиз-сід небезпечний: «майнкрафт» затягнув увесь всесвіт гри (скачати/грати) - ∑3 млн сміття. Франшизу бери в зв'язці зі словом категорії («майнкрафт фігурки») або з url-keywords конкурентів.

## Крок 3. Перевірка покриття - це і є «правильне покриття»
Злий усі джерела (union, максимальна частотність на ключ). Виміряй, який % ключів конкурентів потрапив у твоє ядро:
```
python scripts/coverage_check.py <твоє_ядро.csv> <конкурент_url.csv> [ще_url.csv ...]
```
Скрипт дає % покриття ключів і обсягу + список ТОП пропущеного. **<85% → добери сіди чи url** за підказкою скрипта й повтори. Підсумковий % покриття і джерела - на аркуш «Зведення».

## Крок 4. Чистка - універсальний порядок (гео → інфо → дедуп)
1. **Гео / майданчики / сміття** → «Видалено». E-commerce: `reference/minus_geo_market.txt`; **послуги** з гео-прив'язкою: `reference/minus_services.txt` (**без міст UA** - там місто цільове). Обидва генерує `scripts/build_minus.py` з компонентів: `geo/geo_exclude.txt` (РФ + окуповані міста + BY/KZ + РФ-платформи yandex/wildberries/ozon - **завжди, у будь-якій ніші**; RU-МОВУ не чіпаємо - український ринок шукає й російською), `geo/geo_ua.txt` (міста UA + відмінки - лише e-commerce), `market_junk.txt` (маркетплейси + сміття; ⚠ якщо клієнт сам маркетплейс зі списку, прибери його рядок на час прогону). Правиш компоненти → `python scripts/build_minus.py`.
2. із залишку відбери інфо-запити за `reference/info_markers.txt` → аркуш «Інфо».
3. дедуп (нижче).

Порядок саме такий: гео й майданчики відсікаються навіть в інфо-подібних фразах («де в києві купити» → «Видалено» через 'київ', а не «Інфо» через 'де'). Інфо-слова (як/огляд/фото) до гео-мінусу НЕ входять, тому інфо не видаляється, а маршрутизується. `--minus-file` під час збору зручний, але тоді відсіяне не потрапить у «Видалено» і в баланс; для результату, який можна перевірити, мінус застосовуй у пайплайні.

Дедуп:
- **точні дублі** (lowercase, ё→е, схлопнути пробіли) → схлопни, лишається частотніший.
- **варіанти порядку слів / словоформи** (однаковий набір токенів після відсікання закінчень, порядок неважливий: «кросівки жіночі» = «жіночі кросівки», «палатка / палатки / палаткой») - НЕ сміття і НЕ у «Видалено»! Валідні фрази однієї посадкової → лишай У КЛАСТЕРІ. У ∑ кластера - за частотністю (правило від 14.10.2026):
  - **частотність однакова** → це один запит: Google Ads уже склеїв варіанти, і Serpstat ставить усім одне число (палатка / палатки / палаткой = 22 200). У ∑ іде ОДИН раз (головна фраза), решта - з позначкою в «Коментар»: «дубль «<головна фраза>», в ∑ не йде». Одрук в одному слові за тієї ж частотності - теж дубль;
  - **частотність різна** → різні запити, обидва ключі йдуть у ∑.
  Просте додавання всіх варіантів завищує попит (категорія «Туризм»: 2,78 млн проти 1,70 млн/міс, ×1,6), видалення всіх варіантів - занижує. Розмічає скрипт, а не око: `python scripts/variant_dedupe.py <ядро.xlsx|csv>` (додає колонки «Дубль» так/ні і «Головна фраза»). Дедуп за набором токенів (одне перефразування на ключ незалежно від частотності) - лише для окремого аркуша «Відстежувані» (сервіс позицій), якщо він є.
- явно нерелевантні; спірні НЕ видаляй сам - списком «на питання тімліду».

**Тематична релевантність** (скрипт не судить, потрібне око): «кав'ярня» = заклад ≠ кава-продукт; «кава з кардамоном» = серіал; «майнкрафт скачати» = гра; «панама» = країна чи фільм. Таке - спірним списком тімліду, а не в кластери мовчки. Сюди ж **крива розкладка** («gkfyitn» = «планшет» наосліп) - список її не бере (вона нескінченна), лови оком чи детектором.

**Граблі підрядків** (перевірено): «фіо**лето**ві» ≠ лето, «еко**кожа**» ≠ кожа, «свадь**бу**» ≠ б/у, «**Киров**» ≠ Киев, «якутськ» ≠ «як», «синтетичні» ≠ синій, «сумка» ≠ Суми. Міста, короткі бренди, сезони матчити лише за межею слова - `is_minus` у `scripts/serpstat_api.py` так і працює; свої перевірки пиши так само. Відмінки міст токен-матч не ловить («у києві» ≠ «київ») - відмінки топ-міст уже заведені в `geo_ua.txt` / `geo_exclude.txt`; нову морфологію додавай туди й перегенеровуй.

## Крок 5. Інтент кожного ключа
- **commercial**: купити/купить, ціна/цена, замовити/заказать, доставка, недорого, магазин, оптом.
- **informational**: питання, гайди, порівняння без наміру купити (→ аркуш «Інфо»).
- **navigational**: бренди. Свій бренд - окремий кластер; чужі бренди-майданчики - «Видалено».

Різний інтент = різні кластери.

## Крок 6. Фасетна кластеризація - конфіг ніші + `scripts/semantic_core.py`
Кластеризацію не пиши щоразу заново: опиши нішу в конфігу, а розкладку зробить скрипт. Ти вирішуєш, ЩО є ознакою ніші, скрипт детерміновано рахує, КУДИ йде кожен ключ.

Спершу визнач ГОЛОВНУ вісь ніші, вона в усіх різна:
- одяг / взуття / аксесуари → **стать**, далі бренд / сезон / колір / матеріал;
- техніка / електроніка → **бренд > модель**, далі числові ознаки (потужність, ємність, діагональ, пам'ять);
- іграшки → **франшиза**, далі тип;
- FMCG / їжа → **форма / вид** (кава: зернова / мелена / розчинна), далі бренд і вага.

Конфіг `clients/<проєкт>/semantics/config.json` (повний приклад - `examples/zaryadni-stantsii.config.json`):
- `inputs` - вивантаження з Кроків 1-2 (csv keyword, volume; файли `seed_*` - сіди, решта - конкуренти);
- `minus_lists`, `info_extra`, `topic_rules` (чужі теми з причиною, `unless` - виняток), `numeric_limits`, `require_pattern` (ключ без ознаки категорії й без бренду - у «Видалено»);
- `brands` - назва, slug, regex з кирилицею й латиницею, `models` (regex моделі), `series` (серії без номера); `aliases` - кирилиця в назвах моделей («дельта» → delta, «макс» → max);
- `numeric` - числові ознаки з одиницями (потужність Вт/кВт, ємність Вт·год): «2000 вт», «2квт» і «2 kw» дають одну сторінку «2 кВт»;
- `attributes` - призначення, тип, ціна; `override: true` для аксесуарів («сонячна панель для станції bluetti» - сторінка панелей, а не бренду);
- `combos` - які пари ознак можуть бути окремими сторінками («Для дому > 2 кВт»);
- `thresholds` - поріг сторінки: за замовчуванням >= 3 ключі і >= 50 запитів на місяць.

```
python scripts/semantic_core.py clients/<проєкт>/semantics/config.json
```
Скрипт для кожного ключа будує кандидатів від найдетальнішого до загального: бренд > модель → бренд > серія → бренд > потужність → бренд; поєднання ознак → число → атрибут → база. Ключ іде на найдетальнішу сторінку, де фактично набирається поріг; дрібні сторінки розформовуються, ключі піднімаються на рівень вище. Сторінки брендів лишаються навіть малими. Дублі з однаковою частотністю (`variant_dedupe.py`) лишаються в кластері, але в ∑ не йдуть. Скрипт сам перевіряє баланс «вхід = кластери + інфо + видалено».

Правила:
- Один кластер = одна посадкова. Посадкова: наявний URL (PROJECT.md, sitemap, позиції), інакше «створити: /slug/» - скрипт пропонує адресу зі slug ознак.
- **Списки брендів і атрибутів доменні й за замовчуванням неповні.** Джерело - ДАНІ, а не пам'ять: `python scripts/brands_from_competitor.py <url категорії конкурента>`; готові списки - у `reference/brands/<ніша>.txt`.
- **Обов'язково - аудит «бази»:** `python scripts/cluster_gaps.py <ядро.xlsx>` покаже часті токени в «... (база)» - пропущені бренди, моделі, атрибути. Додай їх у конфіг і перезбери, доки в базі не залишиться очевидних ознак. Межі слова обов'язкові (`jack` ≠ «panama jack»).

## Крок 7. Перевірка видачі - `scripts/serp_check.py`
Детальна сторінка потрібна, лише якщо Google відповідає на неї інакше, ніж на батьківську. Для кожної сторінки (крім бази й брендів) скрипт бере топ-10 за її головним ключем і за ключем батьківської:
- спільних адрес >= 4 - намір той самий, сторінку злити з батьківською;
- інакше, якщо >= 3 результати саме про уточнення (в адресі чи заголовку «2-kvt», «ac180», «kabel») - сторінка окрема;
- інакше видача уточнення не виділяє - злити.

```
python scripts/serp_check.py clients/<проєкт>/semantics/<проєкт>_semantics_<дата>.pages.json --dry-run
python scripts/serp_check.py clients/<проєкт>/semantics/<проєкт>_semantics_<дата>.pages.json --max-usd 2
python scripts/semantic_core.py clients/<проєкт>/semantics/config.json --serp clients/<проєкт>/semantics/serp_check.json
```
⚠ DataForSEO платний (~$0.002 за запит): спершу `--dry-run`, назви тімліду кількість запитів і суму, дочекайся «ок». Запасне джерело - `--source serpstat` (топ з бази g_ua, без заголовків). Відповіді кешуються в `cache/serp/`. Повторюй `semantic_core.py --serp` → `serp_check.py`, доки рішення не перестануть змінюватися (зазвичай 1-2 кола; злиті раніше сторінки перевіряються щоразу заново).

## Крок 8. Друга думка - `scripts/ai_review.py` (ChatGPT)
Регулярки не бачать смислу, тому кожен ключ читає друга модель у контексті своєї сторінки за інструкцією `reference/ai_review_prompt.md`: не про товар, краще на іншій сторінці, інформаційний, незрозумілий.

```
python scripts/ai_review.py clients/<проєкт>/semantics/<проєкт>_semantics_<дата>.pages.json --dry-run
python scripts/ai_review.py clients/<проєкт>/semantics/<проєкт>_semantics_<дата>.pages.json --max-usd 3
```
⚠ Платно (OpenAI): спершу `--dry-run`, назви тімліду кількість запитів і оцінку, дочекайся «ок».

**Знахідки - підказка, а не рішення: модель помиляється.** Перевір їх сам і перенеси підтверджені в конфіг **правилом** (regex на клас запитів, а не ручний список ключів): `topic_rules`, бренди й аліаси, атрибути. Хибні знахідки, які ти відхилив (наприклад, «ціна», «недорого», «розстрочка» модель любить називати інформаційними), - у `ai_dismiss`. Потім:
```
python scripts/semantic_core.py clients/<проєкт>/semantics/config.json --serp .../serp_check.json --ai .../ai_review.csv
```
Скрипт порахує, скільки знахідок враховано правилами і скільки відхилено, а решту позначить у колонці «Коментар» («ШІ: не про товар - ...») на рішення тімліда. Після великих правок - ще одне коло перевірки видачі.

## Крок 9. Результат - один xlsx
`semantic_core.py` пише `clients/<проєкт>/semantics/<проєкт>_semantics_<дата>.xlsx`; копію здачі клади в `deliverables/`. Аркуші:

1. **Кластери**: Keyword | Volume | Group | URL | Інтент | Коментар + колонки ознак (Бренд | Модель | Потужність | ...) для фільтрів і зведених таблиць; у кожної групи підсумковий рядок із ∑ і кількістю ключів;
2. **Структура**: Рівень | Сторінка | Батьківська | URL | Ключів | ∑ | Головний ключ | Перевірка видачі - дерево сторінок;
3. **Інфо**: ті самі колонки, що в «Кластери»;
4. **Видалено**: Keyword | Volume | Причина;
5. **Зведення**: вхід, кластери, баланс, дублі, поріг, перевірка видачі, перевірка ШІ, причини видалення. % покриття (Крок 3) і джерела допиши в резюме тімліду.

## Мова
Одна мова на результат - НЕ універсальне правило. Збираємо всі релевантні (для ринку UA зазвичай RU + UA), позначаємо чи ділимо за мовою; остаточний поділ - за проєктом: десь RU+UA разом, десь RU/UA окремими аркушами. Мову визначай за фразою (кава = uk, кофе = ru), а не за доменом.

## Чек-лист перед здачею
- [ ] Тип ніші визначено; збір багатоканальний (сіди всіх форм + url-keywords конкурентів)
- [ ] **Покриття виміряне скриптом ≥85%**; цифра й джерела - у резюме тімліду
